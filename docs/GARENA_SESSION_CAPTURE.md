# Garena Shop2Game session capture guide

The `garena` provider normally needs no captured cookie. It opens the official
Shop2Game login page, keeps server-issued cookies in a domain-scoped in-memory
session, and retries once when a challenge response rotates the cookie. No
short-lived Garena/DataDome value is bundled in source.

This guide explains the optional recovery workflow when the normal managed
session still requires human verification. It uses a real Chrome or Edge
session with verification completed manually. It does not generate, forge, or
bypass a DataDome challenge.

## What the provider needs

The important values are usually:

| Value | Where it comes from | Purpose |
|---|---|---|
| `datadome` cookie | `shop2game.com` browser cookie | Identifies the verified DataDome browser session |
| `session_key` cookie | `shop2game.com` browser cookie | Associates requests with the Shop2Game session |
| `x-datadome-clientid` | Request header, when present | Sends the DataDome client ID explicitly |
| `source`, `region`, `language` | Browser cookies | Preserves Shop2Game storefront/session context |
| `User-Agent` and `sec-ch-ua*` | Generated by the browser | Describes the browser that created the session |
| `Origin`, `Referer`, `Accept`, `Content-Type` | Request headers | Describes the Shop2Game request context |

DataDome's official documentation says that `X-DataDome-ClientID` takes
priority when present; otherwise the `datadome` cookie value is used as the
client ID. See [DataDome Protection API — Identifying the ClientID](https://docs.datadome.co/reference/validate-request).

Treat any manually captured cookie string as a credential. Store it only in
server environment variables; do not commit it, paste it into issue reports,
expose it in frontend JavaScript, or include it in application logs.

## 1. Create a valid browser session

1. Open Chrome or Edge using the network from which the lookup will normally
   run. A dedicated browser profile is recommended so the captured cookies are
   easy to identify.
2. Open:

   ```text
   https://shop2game.com/app/100067/idlogin
   ```

3. Open Developer Tools:

   - Windows/Linux: `F12` or `Ctrl+Shift+I`
   - macOS: `Cmd+Option+I`

4. Select **Network** and enable **Preserve log**.
5. Reload the page while Developer Tools remains open.
6. Enter a real Free Fire UID and submit it.
7. If Shop2Game displays verification, complete it manually in that browser.
8. Submit the UID again and confirm that the response contains a nickname and
   region rather than a `captcha-delivery.com` URL.

Chrome records requests while the Network panel is open and supports inspecting
their headers, cookies, payload, and response. See the official
[Chrome DevTools Network reference](https://developer.chrome.com/docs/devtools/network/reference/).

## 2. Find the account lookup request

In the Network filter box, search for:

```text
player_id_login
```

Select the request whose URL is:

```text
https://shop2game.com/api/auth/player_id_login
```

Verify these details before copying anything:

- Method: `POST`
- Status: normally `200`
- Request payload contains:

  ```json
  {
    "app_id": 100067,
    "login_id": "PLAYER_UID",
    "app_server_id": 0
  }
  ```

- Successful response contains fields similar to:

  ```json
  {
    "nickname": "PLAYER NAME",
    "region": "BD"
  }
  ```

If the response contains a `geo.captcha-delivery.com` URL, the session has not
yet passed verification and should not be captured as a working session.

## 3. Capture the complete request accurately

The safest manual method is:

1. Right-click the successful `player_id_login` request.
2. Select **Copy → Copy as cURL**.
3. Paste it temporarily into a local text editor that is not synced or shared.
4. Locate the request headers without running or publishing the command.

Chrome officially supports **Copy as cURL** from the Network panel. It also
warns that cookies and authorization values are sensitive and excludes them
from sanitized HAR exports. See
[Chrome DevTools network export and copy options](https://developer.chrome.com/docs/devtools/network/reference/#copy).

The copied command may contain headers such as:

```text
accept: application/json
accept-language: en-US,en;q=0.9
content-type: application/json
origin: https://shop2game.com
referer: https://shop2game.com/app/100067/idlogin
user-agent: Mozilla/5.0 ...
sec-ch-ua: ...
sec-ch-ua-mobile: ?1
sec-ch-ua-platform: ...
x-datadome-clientid: ...
cookie: datadome=...; session_key=...; source=...; region=...; language=...
```

Do not invent `User-Agent` or `sec-ch-ua*` values. Let the browser generate
them, then copy them from the same successful request. Client-hint headers can
change with browser versions.

## 4. Read individual cookies in DevTools

If **Copy as cURL** does not show a value clearly:

1. Open **Application** in Developer Tools.
2. Expand **Storage → Cookies**.
3. Select `https://shop2game.com`.
4. Find these names:

   - `datadome`
   - `session_key`
   - `source`
   - `region`
   - `language`

5. The Network request's **Cookies** tab shows which cookies were actually sent.
   Prefer the cookies attached to the successful `player_id_login` request over
   unrelated analytics cookies.

Analytics cookies such as `_ga` and `_fbp` can be copied if reproducing the
source request exactly, but the lookup integration should first use only the
cookies that were actually required by the successful request.

## 5. Build the two provider environment variables

The private build's current values live only in
`src/Credentials/BundledCredentialProvider.php`. A complete environment group
overrides that bundled group, so rotation does not require a source edit.

Create one semicolon-separated cookie string. Do not add the leading `Cookie:`
label:

```dotenv
GAME_LOOKUP_GARENA_COOKIE="datadome=REPLACE_ME; session_key=REPLACE_ME; source=mb; region=MA; language=ar"
GAME_LOOKUP_GARENA_DATADOME_CLIENT_ID="REPLACE_WITH_X_DATADOME_CLIENTID"
```

When the successful request has no `x-datadome-clientid` header, use the
`datadome` cookie value for
`GAME_LOOKUP_GARENA_DATADOME_CLIENT_ID`. This matches DataDome's documented
client-ID fallback behavior.

The provider also includes browser-like request headers. If Shop2Game changes
them, update the defaults in:

```text
src/Providers/GarenaProvider.php
```

Never duplicate live cookie values in documentation or a public `.env.example`
file. See [`CREDENTIAL_MANAGEMENT.md`](CREDENTIAL_MANAGEMENT.md) for the shared
resolution and rotation rules.

## 6. Configure a local PHP server

### PowerShell

Set values only in the current terminal session:

```powershell
$env:GAME_LOOKUP_GARENA_COOKIE = 'datadome=...; session_key=...; source=mb; region=MA; language=ar'
$env:GAME_LOOKUP_GARENA_DATADOME_CLIENT_ID = '...'
php -S 127.0.0.1:8765 -t template
```

Closing that terminal removes the variables.

### Linux/macOS shell

```bash
export GAME_LOOKUP_GARENA_COOKIE='datadome=...; session_key=...; source=mb; region=MA; language=ar'
export GAME_LOOKUP_GARENA_DATADOME_CLIENT_ID='...'
php -S 127.0.0.1:8765 -t template
```

## 7. Configure shared hosting or cPanel

Use the hosting provider's environment-variable or application-settings UI
when available:

1. Add `GAME_LOOKUP_GARENA_COOKIE`.
2. Add `GAME_LOOKUP_GARENA_DATADOME_CLIENT_ID`.
3. Restart PHP-FPM/application workers if the host provides that action.
4. Confirm PHP can read the variables server-side.

Temporary diagnostic check:

```php
<?php
header('Content-Type: application/json');
echo json_encode([
    'cookie_configured' => getenv('GAME_LOOKUP_GARENA_COOKIE') !== false,
    'client_id_configured' => getenv('GAME_LOOKUP_GARENA_DATADOME_CLIENT_ID') !== false,
]);
```

Delete this diagnostic file immediately after testing. It deliberately reports
only booleans and must never print the credential values.

If the host does not allow environment variables, place secrets in a PHP config
file outside `public_html`, load that file server-side, and pass `cookie` and
`dataDomeClientId` in the provider configuration. Ensure the file cannot be
downloaded over HTTP.

## 8. Test the provider

In the local tester:

1. Select **Free Fire**.
2. Enter an 8–12 digit UID.
3. Select **Only garena**.
4. Enable **Bypass cache**.
5. Click **Check account**.

Expected successful JSON:

```json
{
  "ok": true,
  "code": "SUCCESS",
  "nickname": "PLAYER NAME",
  "provider": "garena",
  "country": "BD",
  "meta": {
    "http_status": 200,
    "challenge_credentials_configured": true
  }
}
```

The Shop2Game `region` field is normalized to the package's top-level `country`
field. It may be a country code such as `BD` or a broader regional identifier.

## 9. Troubleshooting

| Result | Likely cause | Action |
|---|---|---|
| `challenge_credentials_configured: false` | PHP did not receive the environment variables | Restart PHP and verify variable names with the boolean diagnostic |
| HTTP `403` plus `captcha-delivery.com` | Cookie expired, verification incomplete, or session/network changed | Reopen Shop2Game, complete verification manually, and capture a new successful request |
| `error_params` | Request payload/session combination was rejected | Confirm `app_id=100067`, `app_server_id=0`, UID format, cookies, and headers came from the same request |
| Works locally but fails on hosting | Session may be tied to network/browser context, or outbound requests are restricted | Capture from the intended network when possible and ask the host whether outbound HTTPS to Shop2Game is allowed |
| HTTP `200`, nickname present, country missing | Upstream response omitted `region` | Inspect the successful response and update the configured country path if Garena changed its schema |
| Previously worked, now returns `403` | DataDome or Shop2Game rotated/expired the session | Capture fresh values; do not assume a cookie is permanent |

## 10. Rotation checklist

When credentials stop working:

1. Open the same dedicated browser profile.
2. Visit the official Shop2Game player-ID page.
3. Complete any displayed verification manually.
4. Capture a new successful `player_id_login` request.
5. Update both environment variables together.
6. Restart PHP workers.
7. Test with **Only garena** and **Bypass cache**.
8. Remove old values from shell history, notes, screenshots, and deployment logs.

The `datadome` cookie, `session_key`, and matching client ID should be treated as
one rotating session set. Mixing values from different browser sessions is a
common cause of HTTP `403` responses.
